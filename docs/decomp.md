# Matching build

The Simulation disc executable (`SCUS_944.88`) and its six uncompressed overlays can be rebuilt byte for byte from the disassembly. This is the base for a matching decompilation: functions are rewritten in C++ one at a time, with each build checked against the originals. So far the OVL3 functions are C++, and so are their copies in other overlays, which build the same sources: `Max3`, `Min3`, `Rgb555_ToHsv`, `RaceCarPick_Random`, `RaceCarPick_SetColor` and `RaceSetup_InitEvent` (also in OVL1, OVL2 and OVL4), `RaceSetup_SetCarFromEntry` and `RaceSetup_SetCarFromGarage` (also in OVL2 and OVL4), `CarWork_Clear`, `CarWork_LoadParts` and `CarWork_SetStagesFromSetup` (twice in OVL4), `Car_StoreSetup` (also in OVL4), and `ArcadeSel_SetupRaceCars`, `ArcadeSel_LoadGarageCar`, `CarWork_LoadGarageCarAlt` and `ArcadeGarageRace_Entry` (OVL3 only). All 55 functions of OVL5 (the movie player) are C++: the player (`Movie_*`), its CD stream ring (`MovieStream_*`), the MDEC output (`MdecOut_*`), the `psxMovieLoop` screen loop and the movie entries. `psxMovieLoop` is a real C++ class, derived from the resident `psxViewLoop` and `ScreenViewLoop`, which `viewloop.h` declares in vtable order. `movieloop.cpp` emits its vtable, type name, `__tf` function and typeinfo, and defines the overlay's buffers in `.bss`. The rest of OVL5's `.rodata` (the VLC table and the display positions) is still the original data. In OVL4 (GT mode), 247 more functions are C++, in 21 files under `src/sim/ovl4/` that keep the others as `INCLUDE_ASM`: the screen loops `GTMenu`, `GTLoadingMenu` and `GTBattleMenu` are real classes, and the rest is Ghidra's decompilation as it is ([OVL4](#ovl4)). The Sony PsyQ library code in the EXE is linked from the original library objects ([psyq-libs.md](psyq-libs.md)), and the C++ runtime from GCC 2.8.1's `libgcc`, compiled from the GNU sources ([runtime-libs.md](runtime-libs.md)). All 27 functions of the game's own C library (`syslib`) are C, built with GCC 2.95.2 and GNU as: `Sys_Init`, `memset`, `strcpy`, `strcmp`, `sprintf`, `strncpy`, `strlen`, `memcpy`, `strcat`, `strncasecmp`, `malloc`, `abs`, `memcmp`, `Printf_EmitString`, `Printf_EmitNumber`, `Printf_FormatDec64`, `Printf_FormatOct64`, `Printf_FormatHex64`, `Printf_ParseInt`, `Printf_Format`, `InitHeap`, `Heap_InitDefault`, `free`, `Printf_PutcToBuffer`, `vsprintf`, `Heap_SplitBlock` and `Heap_MergeNext`, in `src/sim/exe/syslib.c`, with its `.rodata` (the hex digits and `Printf_Format`'s jump tables) ([C sources](#c-sources)). 538 of the 786 functions of the game's resident code are C++, in 44 files under `src/sim/exe/` that keep the others as `INCLUDE_ASM`: `ScreenViewLoop`, `psxViewLoop` and `psxViewLoopDoubleBuffer` are real classes, and the rest is Ghidra's decompilation as it is ([Resident code](#resident-code)). In the boot code, the splash screen class `VendorBootLogo` and `Boot_Init` are C++ too (`src/sim/exe/bootlogo.cpp`). Everything else is assembly.

The disassembly comes from [splat](https://github.com/ethteck/splat) and uses the names from the Ghidra project ([ghidra-setup.md](ghidra-setup.md)). Only the configs, the symbol files and the build script are in the repo. The original files and everything generated from them stay outside git.

## Requirements

Linux, or WSL on Windows (Ubuntu 24.04 is what this was tested on):

```bash
sudo apt install binutils-mipsel-linux-gnu python3-venv cpp
cd decomp
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
python3 tools/setup_toolchain.py
```

- `requirements.txt` pins splat 0.50.1 (with spimdisasm and rabbitizer).
- The build uses GNU binutils 2.42 (`mipsel-linux-gnu-as`, `ld`, `objcopy`); set `CROSS` to use another prefix.
- `setup_toolchain.py` downloads the compilers (GCC 2.8.1 for the game, GCC 2.95.2 for its C library), and the GCC 2.8.1 sources of the runtime the EXE links, into `tools/toolchain/` (ignored), checking pinned SHA-256s. See [Compiler](#compiler).

## Building

```bash
cd decomp
.venv/bin/python tools/build.py
```

For each unit (`exe`, `ovl0` … `ovl5`) this runs splat if its output is missing, assembles every file, converts the PsyQ library members the unit uses into `build/psyq/<lib>.a` (`tools/psyq.py`), compiles its libgcc objects into `build/psyq/libgcc.a` (`tools/libgcc.py`), links with the splat linker script, extracts the binary with `objcopy` into `build/sim/`, and compares its SHA-1 with the one in the unit's yaml. It prints `OK` or `DIFF` per unit and exits non-zero on any difference. Pass unit names to build only those, and `--split` to re-run splat after changing a yaml or a symbol file.

Each overlay is linked on its own at `0x80010000`, against the resident symbols, which splat writes to `build/sim/<unit>.undefined_*_auto.txt` as absolute addresses. The EXE has three segments: the PS-X EXE header, the boot code (`0x80010000`, overwritten by the first overlay) and the resident code (`0x8005d600`). The resident segment links the PsyQ members and the libgcc objects from `build/psyq/` with splat's `lib` subsegments, and `build.py` adds their `.bss` to the linker script as `build/sim/exe.psyq.ld`. For OVL5, `build.py` writes `build/sim/ovl5.cxx.ld`: it places the overlay's `.bss` at `0x800a8d5c` (`BSS_VRAM`), where the overlays' BSS starts, and defines the g++ names that its C++ classes reference (`Enter__11psxViewLoop`, `__ti11psxViewLoop`...) as the exported names (`CXX_NAMES`).

## Symbols

[`scripts/ghidra/export_splat_symbols.py`](../scripts/ghidra/export_splat_symbols.py) writes `decomp/sim/symbols/`:

- `exe.txt`: boot and resident functions, and the main-space labels.
- `ovlN.txt`: overlay N's functions and labels (including its BSS view from `overlay_bss.py`), then the resident ones. An overlay label wins over a main-space label at the same address.

It exports every function (a thunk only when it has a name of its own, like `CdGetSector_Thunk`; otherwise it takes its target's name), and the labels named by hand or by the PsyQ signatures that are not inside a function. Names are made valid for the assembler (`ArcadeMenu::Enter` becomes `ArcadeMenu__Enter`, `~ArcadeMenu` becomes `ArcadeMenu_dtor`), and a duplicate within a unit gets its address appended.

After renaming things in Ghidra, run the script (Script Manager, category **GT2**, or ReVa `run-script` with `OUT_DIR` set when the script is run inline), then `tools/build.py --split`. The build must still match: names never change the bytes.

## What it took to match

- **Section alignment.** GNU as gives every section 16-byte alignment, and the linker would pad between them. The configs set `subalign: 4` (the original sections follow each other on 4-byte boundaries) and turn off splat's segment and section end alignment.
- **Strings.** splat decodes EUC-JP and Shift-JIS text and writes it as UTF-8, which as stores as UTF-8, so the configs restrict string detection to ASCII. Other text stays as `.word`.
- **Data inside code.** OVL0 has three tables inside its code (`0x8002ee98`, `0x80046bac`, `0x800489d8`). They contain words that decode as MIPS III instructions, which as rejects for the R3000. They are `textbin` subsegments (raw bytes kept in `.text`), so they stay at their address.
- **Boot data.** The boot code and its data (`0x80011d30`, mostly zeros after `0x80033de2`) are their own segment. In one segment with the resident code, the linker would move the boot data after the resident code.

## Compiler

The game's libraries match PsyQ 4.6 (libpad 4.7; see [psyq-libs.md](psyq-libs.md) for the objects and how to link them), but its code was not built with the PsyQ 4.6 compiler, which is GCC 2.95.2. It matches Sony's GCC 2.8.x builds, the compilers of PsyQ 4.3 (GCC 2.8.0) and PsyQ 4.4 (GCC 2.8.1), so the game used an older compiler with the newer libraries. The game code is C++ built with `-O2 -g0 -G0 -fvtable-thunks -fno-exceptions -fno-builtin` (constructors and destructors of OVL5's `psxMovieLoop` have no exception cleanups, and the flag changes nothing elsewhere; `ReplayDir_Init` and `SaveFile_InitHeader` call `memcpy` for a 0x20- and 0x80-byte icon, which GCC's builtin `memcpy` copies inline, and `-fno-builtin` changes nothing else in the build). Its vtables have the thunk layout (0, the `__tf` function, then 4-byte function pointers), and the EXE header's `gp` is 0. The C++ runtime linked with it (`__main`, RTTI, `__divdi3`) is GCC 2.8.1's own `libgcc`, built with `-fexceptions`; [runtime-libs.md](runtime-libs.md) has it and the game's libc.

The build uses the same open-source toolchain as decomp.me's `gcc2.8.1-psx` compiler:

- **GCC 2.8.1** rebuilt from GNU sources with a PlayStation target (`mips-sony-psx`: R3000, little endian, soft float, unsigned `char`), [decompals/old-gcc](https://github.com/decompals/old-gcc) release 0.17. Only `cc1plus` is used. The game's C library was built with a newer compiler ([C sources](#c-sources)).
- **[maspsx](https://github.com/mkst/maspsx)** at the decomp.me commit (`4ffa8b5`). It rewrites the compiler output the way Sony's ASPSX assembled it, then runs GNU as. `--aspsx-version=2.86` (ASPSX of PsyQ 4.6) makes small `li` constants `addiu`, as in the game; with `-G0`, maspsx treats ASPSX 2.79 (PsyQ 4.4) the same.
  `setup_toolchain.py` patches one rule: after a `div`, maspsx adds a `nop` when the next instruction reads the quotient, even past a label. The game has no `nop` there in `Rgb555_ToHsv` (OVL3), so the patch makes it match. Sony's ASPSX 2.79 and 2.86 do add the `nop`, though, so the original source probably differs from ours before that branch, and the patch may be dropped once it does.
  Sony's ASPSX, run under wibo with maspsx's own test setup (`aspsx/`, the binaries from its `aspsx` release), adds that `nop` in every version from 2.56 to 2.86, with or without `-0` (which only drops the division checks): after `divu` and an `sltu` that reads the quotient, after `div` and a `sw` or `sh` of it, and past a label before a `beq` on it. ASPSX also puts a label before a load delay `nop`, so a jump to it lands on the `nop`. maspsx copies all of this correctly. The game has no such `nop` in any of its 7 places where an instruction reads the quotient right after the `mflo`, so that code wasn't assembled by ASPSX. One of them is `Credits_FormatCommas`, which matches with GNU as ([Format](#resident-code)); the other 6 are in functions that don't match yet, in files that are still assembled with maspsx.

A `.cpp` file goes through:

1. The host `cpp` (`-nostdinc -undef`, GCC 2.8 and MIPS macros, `-Iinclude`). `# 0` line markers become `# 1`, which `cc1plus` accepts.
2. `cc1plus -quiet -O2 -g0 -G0 -fvtable-thunks -fno-exceptions -fno-builtin`, reading from stdin. The 32-bit compiler can't `stat` files on a Windows drive under WSL (inode numbers overflow), so it gets no file names. Its output is kept as `build/sim/src/.../<file>.cpp.s` for diffing.
3. maspsx, then GNU as with the same flags as the disassembly.

decomp.me's PsyQ packages (`psyq4.3` to `psyq4.6`) run Sony's executables under wibo. With PsyQ 4.3 and 4.4's `CC1PLPSX.EXE`, the same functions match as with this rebuild, and the ones that don't match here don't match there either: they need a different source, not a different compiler. Sony's ASPSX also checks divisions unless given `-0`; the game has no checks, and maspsx doesn't add them.

## C sources

`syslib` (`0x8008ce08–0x8008dfc4`, [runtime-libs.md](runtime-libs.md#the-games-library)) is the game's libc, and was not built like the game. Its functions have C names (`memset`, `malloc`), and the compilers give the same code for them as C and as C++, so it is C, as a libc would be.

- **GCC 2.95.2.** It is the version of PsyQ 4.6's compiler (PsyQ 4.6 libraries are linked in the EXE), but the library was assembled with GNU as (below), so it may come from a plain GNU toolchain rather than from PsyQ. Its rebuild from [decompals/old-gcc](https://github.com/decompals/old-gcc) (`gcc-2.95.2-psx`, release 0.17) matches 18 functions. GCC 2.8.0 and 2.8.1 match 11 of them and miss `strncpy`, `memcpy`, `InitHeap`, `vsprintf` and `Printf_FormatHex64` by scheduling and register choices. 2.5.7 to 2.7.2 match 3 or 4, and 2.91.66 matches fewer than 2.95.2. No option tried (`-O1`, `-O3`, scheduling and GCSE switches) matches more than `-O2`.
- **Signed `char`.** The library reads characters with `lb` (`strlen`, `strcmp`, `strncasecmp`), where the rebuilt compilers' unsigned `char` gives `lbu`. `build.py` passes `-fsigned-char`, so the sources use plain `char`.
- **Strict aliasing.** In `Heap_SplitBlock`, the load of the new block's `size` is scheduled above the stores to `next` and `prev`, which have pointer type, but not above the store to the other block's `size`. Only type-based alias analysis allows that, so `build.py` passes `-fstrict-aliasing` (off by default in 2.95.2). The other functions match with or without it.
- **Inline assembly.** `memset` stores the unaligned head and tail of the fill with a lone `swr` and a lone `swl`, which the compiler doesn't emit by itself, so the source uses `__asm__` for those two stores.
- **GNU as.** The library was assembled by GNU as, not Sony's ASPSX. When a load is followed by a label and then an instruction that reads the loaded register, ASPSX (and maspsx) put the label first and then the `nop`, so a jump to the label lands on the `nop`. GNU as puts the `nop` before the label. `Printf_ParseInt` jumps past its `nop` (`j` at `0x8008d894`), so it matches only with GNU as. Every other function matches with both. The GNU as of the time encoded `move` as `addu`, where binutils 2.42 uses `or`.
- **Building.** A `.c` file is preprocessed like a `.cpp` file and compiled with `gcc-2.95.2-psx/cc1 -quiet -O2 -g0 -G0 -fsigned-char -fstrict-aliasing`. `build.py` rewrites each `move` as `addu` and passes the output straight to GNU as, with the same flags as the disassembly; maspsx isn't used.
- **One file.** `[0x7d608, c, syslib]` is a single `c` subsegment, and `[0x81774, .rodata, syslib]` places its `.rodata`: the two hex digit strings (string literals in `Printf_FormatHex64`) and the three jump tables of `Printf_Format`'s switches. GCC aligns the tables to 8 bytes within the section, which starts at `0x80090f74`, only 4-byte aligned; splat's linker script puts every input section on 4 bytes (`SUBALIGN(4)`), so the tables land at their original offsets.

## Decompiling a function

[matching-quirks.md](matching-quirks.md) collects the source forms that give the game's code, and the patterns no form has matched yet.

1. In the unit's yaml, give the function's address range its own subsegment: `[0x0, cpp, carwork]` makes `src/sim/<unit>/carwork.cpp`, and the next `asm` subsegment starts after the function.
   A function that another unit has too uses that unit's file: OVL4's `[0x5404, cpp, ../ovl3/carwork]` builds `src/sim/ovl3/carwork.cpp`. `build.py` creates `src/sim/<unit>/` before splitting, so the `..` resolves and splat sees the existing file.
   When the copy has other names there (`Demo_PickRandomCar` in OVL1, the `_OVL2` suffixes, OVL4's second CarWork copy), the unit gets its own file that `#define`s them and `#include`s the shared source, as `src/sim/ovl1/randompick.cpp` does.
2. Write the function in that file. Keep it `extern "C"` (see `include/common.h`) while its callers are assembly, so the symbol keeps the name the disassembly uses.
3. Run `tools/build.py --split <unit>`, and compare `build/sim/src/.../<file>.cpp.s` with the original assembly until the unit prints `OK`.

splat never overwrites an existing source file.

## Resident code

The game's resident code (`0x8005d600` to the libgcc block at `0x80085974`) is split into 63 subsegments, one per group of related functions (`vol`, `records`, `garage`, `carmodel`, `cardmenu`, `seq`, `cdaudio`, `viewloop`...). The boundaries follow the function names, since the code shows no object boundaries (no padding between objects). The 44 groups with at least one matched function are `cpp` files; their other functions are `INCLUDE_ASM("asm/sim/exe/nonmatchings/<file>", <name>)`, from the asm files splat writes for a `cpp` subsegment. The 19 others are still `asm` subsegments. `start`, `setjmp` and `longjmp` stay assembly.

- **First pass.** Each function was tried once with Ghidra's decompilation unchanged, compiled on its own and compared with the original, relocations masked. 204 matched, and are in the files as Ghidra wrote them (with `uint`, `undefined4` and the like spelled out as C types, and the trailing `return;` dropped). A few match only with a signed type where Ghidra has an unsigned one (`signed char`, `short`); their source spells it. 579 don't match yet, mostly from different code shapes (Ghidra's loops and expressions, globals that start inside a table, field signedness), Ghidra's partial-variable syntax, or switch tables.
- **Types.** `include/resident.h` is Ghidra's `DataTypeWriter` export of the types the matched code uses, adapted for `cc1plus`: enums become integer typedefs of their Ghidra size with the constants in an anonymous enum (two enums share constant names), fields named like C++ keywords get a `_`, and `bool` is a byte as in Ghidra (GCC 2.8.1's `bool` is 4 bytes). It checks with the Ghidra sizes and field offsets of all 231 structures except the ISO 9660 records `IsoContext` and `IsoDirRecord`, whose fields are not aligned. `McDirEntry.next` is `signed char`: the code stores -1 there.
- **ScreenViewLoop.** `screenviewloop.cpp` (`0x800833a0-0x800834fc`) is the class itself: constructor, destructor, `Execute`, `Run`, the four empty steps, and what g++ emits with them, the `__tf` function, the vtable and the type name (its `.rodata` subsegment at `0x800908ec`) and the typeinfo (`.comm`, placed at `0x801c9400`). The assembly that is left (the boot logo, `psxViewLoop`) references it by the Ghidra names, so `build.py`'s `CXX_NAMES` for the EXE defines them as the g++ names (`ScreenViewLoop__Run = Run__14ScreenViewLoop`), and `__ti14ScreenViewLoop` as the typeinfo's address. The file is assembled by GNU as instead of maspsx (`GAS_CXX`): in `Run`, the loop's `j` lands after the load delay `nop` that comes before the label, which only GNU as gives, as in syslib's `Printf_ParseInt`. With GCC 2.95.2 it doesn't match, and assembling all the C++ with GNU as breaks the other units, so it is a property of this file (perhaps the screen loop classes came from a separate library). `format.cpp`, `cardmenu.cpp`, `carinfo.cpp`, `carmodel.cpp` and `cdaudio.cpp` are the other `GAS_CXX` files; for all six, `build.py` writes GCC's `div`/`divu` macros out as `div $0` and `mflo` (`mfhi` for `rem`), since GNU as would expand the macros with division checks.
- **psxViewLoop.** `viewloop.cpp` (`0x80080820-0x80080eec`) derives from `ScreenViewLoop`: the static vblank callback `VSyncHandler`, constructor, destructor, `SetVideoMode` and the virtual steps, with its vtable and type name (`.rodata` at `0x800906c8`) and typeinfo (`0x801f0cf0`); the class layout (0x6c bytes) is in `viewloop.h`, which OVL5's `psxMovieLoop` uses. Everything matches. Notes from matching it: `Enter` computes the new buffer index into an `unsigned char` local and stores it after `videoModeDelay` (found with [decomp-permuter](https://github.com/simonlindholm/decomp-permuter); otherwise the allocator gives `g_LastBufferIndex` and the index a0 and a1 the other way round); `vsync` is set by an inline `VSyncCallback` constructor in the initializer list (the original addresses it through its own pointer); the pad raw buffers are `volatile`, and `Step` reads the port's status byte into a local before taking the pointer to its buttons (that keeps `&g_PadSystem` in a register and `result = 0` ahead of the load, as in the original); and `UpdateDisplay` reads the vblank count, `swapPending` and `videoModePending` into `int` locals first.
- **psxViewLoopDoubleBuffer.** `viewloopdb.cpp` (`0x8007fe8c-0x80080088`) derives from `psxViewLoop` and adds the two buffers' VRAM y (`bufferY`, 0x70 bytes): constructor, destructor, `Leave` (flips and draws twice more so both buffers hold the last frame), `SetVideoMode`, `BeginDraw` (the draw area in `g_DrawArea`, offset by the buffer's y; the offset is read first, then the area into `int` locals) and `SwapDisplay`, with its vtable and type name (`.rodata` at `0x80090630`) and typeinfo (`0x801f0ce0`). `Gpu_Reset`, just before it, belongs to the previous group.
- **VendorBootLogo** (boot code). `bootlogo.cpp` (`0x80010a24-0x80010f1c`) derives from `psxViewLoopDoubleBuffer` and shows each splash screen, fading it in and out. The file also has `Boot_ClearVram`, `Boot_ShowSplashScreens` and `Boot_Init`, since g++ emits `__tf14VendorBootLogo` after them, at the end of the file; its `.rodata` (`0x80011d38`) is `Boot_Init`'s `"/"`, then the vtable and type name. Everything matches except `Boot_ShowSplashScreens` (`NON_MATCHING`): its C++ has the original's shape (a `g_VolDir` local next to the symbol, the loop test at the top), but strength reduction gives the byte fields their own pointer, which takes the register the original uses for `D_80033DC0`'s high half; two and a half hours of decomp-permuter on a C version (about 430,000 candidates) didn't remove that pointer either. Notes: a local declared in a loop body makes g++ keep the test at the top (`Boot_ClearVram`); `Draw` needs `left` computed before `level = frame` (load order) and its two constants in locals set before the loop. The splash images (`g_SplashScreens`) stay the original data.
- **Overlay.** `overlay.cpp` (`0x8005d9bc-0x8005db90`) loads the overlays and runs their entries. `Overlay_ClearBss`, `Overlay_Dispatch` (the `setjmp` point that calls each entry with four ints), `Overlay_Start` and `Overlay_StartAt` match. `Overlay_StartAt` is variadic, `(int index, void *entry, ...)`: the game stores `$a1`-`$a3` to their home slots and reads the four ints back from the stack, while keeping `entry` in a register. Its `va_arg` is written out on `__builtin_next_arg(entry)` (`NEXT_INT`), as there is no `stdarg.h`; indexing the argument area directly keeps a pointer in a register, and taking `&entry` puts `entry` in memory. `Overlay_Load` is still assembly, with its C++ under `NON_MATCHING`: the game takes the index through `$a1` and the pack and entry pointers through `$a0` before keeping them in `$s0` and `$s1`, three moves more than GCC gives, and neither inline helpers, references, other orders, GCC 2.95 nor permuter changed that.

- **Seq.** `seq.cpp` (`0x80079140-0x8007ab14`) is the sound driver: the SPU voices (`SfxVoice_*`, keyed on and off and their registers written by `SfxVoices_Update` in the vsync), the reverb setup, and the sequencer (`SeqPlayer_*` play songs from a `SEQG` file on 25 channels; `Seq_Tick` runs their events each vsync and `SeqChannel_UpdateAll` follows their bends, volumes and pans). `resident.h` has its state (`SeqState` for `g_Seq`, `SoundDriver` for `g_SoundDriver`, `SfxVoice`, `SfxParams`) and the instrument bank (`SeqBank`, `SeqProgram`, `SeqRegion`). 17 of its 30 assembly functions now match, so 23 of its 36 functions are C++.   - **Hard float.** Only with `-mhard-float` does GCC load `SfxVoices_Update`'s constants 2, 1 and -1 into registers before its loop, as the game does: the FPU registers then count as free, which raises the loop pass's threshold for moving constants.   - `AddLayer`, `AssignOT` and `Begin` walk the layers as `while ((l = next) != 0) { next = l->next; ... }`, which gives the game's loop (see [Loops](matching-quirks.md#loops)). `AddLayer` reads the new layer's priority into an `int` first, which gives the game's signed `slt`, and sets the new layer's `next` to 0, so the layers after it are dropped from the list.

## OVL4

OVL4 is the GT mode: its menus (`GTMenu`, `GTLoadingMenu`, `GTBattleMenu`), the car dealers, tuning shop and garage, event rules, licenses, the menu pages and their background, the GT font and the menu music. Apart from the functions shared with OVL3, its code (`0x80012c6c-0x80015404` and `0x80016fec-0x80022964`) is split into 26 subsegments, one per group of related functions, like the resident code. - **First pass.** Each of the 297 functions outside the shared ones was tried once with Ghidra's decompilation unchanged, compiled on its own and compared with the original, relocations masked. 79 matched, and are in the files as Ghidra wrote them, with `uint`, `undefined4` and the like spelled out as C types and the trailing `return;` dropped. - **Race data and wheels.** `gtracedata.cpp` (`0x80021a40-0x80021c38`) gets an event of `g_GtModeRaceData` by its index (`GtRaceData_GetEvent`) or its code (`GtRaceData_FindEvent`, a linear search with `strcmp`), finds a wheel's index in table 0x1d (`Wheel_FindIndex`), fits wheels to a `CarSetup` (`CarSetup_SetWheels`: the car's own wheels, code 0, take the entry's other variant when the car's racing modification entry has its byte 0xe set) and returns a wheel's variant (`Wheel_GetVariant`). All 5 functions match.
- **Events.** `events.cpp` (`0x800183ec-0x80018f6c`) classifies events by their codes (`Event_IsProLeague`, `Event_IsWorldLeague`, `Event_IsLicense`, `Event_IsFreeRace`, `Event_GetFreeRaceIndex` and `Event_GetMachineTestType`), checks the leagues won (`Events_AllRegionalLeaguesWon` and `Events_AllProLeaguesWon`, over the code lists `g_RegionalLeagueCodes` at `0x80050bb4` and `g_ProLeagueCodes` at `0x80050bf8`), finds an event's index in `g_EventCodes` through the first-letter index that `Event_BuildLetterIndex` builds, splits a championship code into its base and race count (`EventCode_GetBase`, `EventCode_GetRaceCount`, `EventCode_Format` with `g_EventCodeFmt` at `0x80050c14`), and fills the championship's race list (`ChampRaceList_Build`, with a random course for "none") and the prizes and prize cars of the event about to run (`Event_LoadPrizeInfo`). 17 of its 18 functions match; `ChampRaceList_Build` stays assembly with its C++ under `NON_MATCHING` (two saved registers swapped). The strings it compares with are still the original `.rodata`, as `D_` symbols.
- **Event rules.** `eventrules.cpp` (`0x8001907c-0x80019c60`) has the licenses and the entry rules of the 248 events: `License_IsEarned` (a medal in every test), `License_GetHighest`, `License_IdFromRaceCode2` (from the code's first three letters, `g_LicenseRaceCodes` at `0x80050d04`) and `License_CheckEntry`; `EventRules_BuildAll` and `EventRules_Load` fill `g_EventRules` (prizes, power limit, a word of flags and the allowed cars, which go to `g_EventAllowedCars`) from the GT mode race data; the getters (`Event_IsDirt`, `Event_GetTurboRule`, `EventRules_GetRequiredLicense`, prizes, power limit); `Race_CheckEntry`, which checks the current car against an event (league, dirt tyres, license, drivetrain, turbo, racing modification, power and allowed cars, each with its message page); `Course_PickRandom` and `Event_GetGhostFileId`. 17 of its 18 functions match; `EventRules_BuildAll` stays assembly with its C++ under `NON_MATCHING` (one `lui` scheduled earlier). The flags are a `ushort` read through by-value copies of an `EventFlags` class with inline accessors.
- **Player stats.** `playerstats.cpp` (`0x80019c60-0x80019f5c`) has the totals of the GT mode status page: the races entered and won and the win rate in hundredths of a percent (wins capped at 429,496 so the product fits 32 bits), the average finish times 100 (`PlayerStats_GetRatio50`), the events won (`Events_GetWinPercent`, over the event count less 29), the prize money in two parts, the garage's car count and total value (in units of 100,000,000 and the rest), its most powerful car (`flags98 & 0x3fff`) and the number of license tests holding a medal. All 10 functions match. They reach `g_GameState` through a `GameState *` local, for the game's separate `addiu` of the field offset; `License_CountMedals` declares it in its outer loop, so its address is loaded after the counters are set ([matching-quirks.md](matching-quirks.md)).
- **Dealer.** `dealer.cpp` (`0x80017750-0x800183ec`) buys and sells cars, parts and wheels for a garage: `Dealer_CanBuyNewCar` and `Dealer_BuyNewCar` (the setup completed through `g_RaceCarWork` by `CarSetup_Finalize`, with the tyres that come with the car from `Car_GetIncludedTires`), `Garage_SellCar` (a quarter of the new price), `Tune_CanBuyPart`, `Tune_BuyPart` and `Tune_InstallPart` (through `g_CarWork`: the racing modification sets the car's model and colour, tyres go in both tyre slots), `CarWork_BuildSpecWithPart` for the tuning preview, `GTMode_PreparePlayerCar` (dirt tyres for a dirt race), `WheelShop_BuyWheels`, and the car's prices, names and colour index. 21 of its 24 functions match. - **Shop transactions.** `txn.cpp` (`0x8001da24-0x8001e22c`) is the pending shop transaction, `g_ShopTxn`: the setters for buying a new car, a part or wheels, selling a car and selecting one (`Txn_Set*`), `Txn_PreviewPart` (the part's price, whether the car has it, and the car's power now and with it), `Txn_Back` and `Txn_Decline`, which step back from a confirmation, `Shop_CheckTransaction`, which returns the message page that stops a transaction (money, an empty slot, a part that doesn't fit) or applies a car selection at once, and `Shop_ExecuteTransaction`, which carries it out (`Dealer_BuyNewCar`, `Tune_BuyPart`, `Tune_InstallPart`, `WheelShop_BuyWheels`, `Garage_SellCar`) and returns the message page to show. The four functions' jump tables are the file's own `.rodata` (`0x8002405c-0x80024284`). `ShopTxn.type` is a `short` (`lh`, and its `switch` index is sign-extended). The cases follow the game's block layout, and the assignments after a call are written after it ([matching-quirks.md](matching-quirks.md)).
- **CarWork helpers.** `carwork2.cpp` (`0x80016fec-0x80017750`) works on `g_CarWork`: `CarWork_ExportSetup` copies its setup out, `Part_GetSlot` gives a part's tune slot and stage, `ListCarWork_Load` and `CarWork_LoadFromGarage` load a garage car into `g_RaceCarWorkAlt` or `g_CarWork`, `Tune_DrawInstalledParts` draws the parts fitted to `g_RaceCarWorkAlt`'s car (`g_TuneSummaryRows`), and `RacingMod_FirstVariant` and `RacingMod_NextVariant` step through the racing modification variants. - **Car lists.** `carlist.cpp` (`0x80020198-0x80020c50`) has the garage and used car list widgets, two `MenuList`s (`g_GarageList_Menu`, `g_UsedCarList_Menu`) whose `DrawItem` callbacks draw a row: the blinking highlight box, the maker and name, the colour swatch, and the mark and current car marker (garage) or the price (used cars).
